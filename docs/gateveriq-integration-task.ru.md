# GateVeriq: план доработок для интеграции с Neruvalo

## Задание для агента в репозитории GateVeriq

Доработай GateVeriq по требованиям этого документа. Сначала прочитай применимые
`AGENTS.md`, актуальные исходники и документацию. Затем реализуй изменения,
миграции, тесты, обнови документацию и примеры. Не ограничивайся описанием плана.
Не выполняй push и публикацию без отдельного поручения.

Документ предназначен для работы **в репозитории GateVeriq**. Изменения Neruvalo,
описанные ниже, являются контекстом и контрактом интеграции.

База анализа: ветка `main`, коммит
`34bc6eb3f153f83e909206bd5a03c94f1d6a03ce` от проверки 2026-11-03.
Если код уже обновился, адаптируй реализацию к актуальному состоянию и используй
имеющиеся возможности вместо дублирования. Названия новых полей в этом документе
— предлагаемый контракт; согласуй их с принятым стилем проекта.

## 1. Цель и пользовательские требования

Neruvalo — приложение на Tauri/React с Rust-клиентом, Rust-сервером и
OPAQUE-аутентификацией. GateVeriq используется как отдельный сервис проверки.
Нужен полный браузерный сценарий с PoW и картинками, а не только нативный PoW.

Зафиксированные требования владельца Neruvalo:

1. При регистрации картинки показываются всегда, независимо от истории ошибок.
2. После каждого неверного email-кода перед следующей проверкой кода пользователь
   обязан заново пройти картинки. Успешная проверка не разрешает несколько
   различных попыток ввода кода.
3. Сервер Neruvalo хранит журнал неудачных входов.
4. После второго неудачного входа Neruvalo отправляет письмо владельцу.
5. После третьего неудачного входа Neruvalo блокирует аккаунт и отправляет письмо
   со ссылкой разблокировки.
6. Для разблокировки владелец переходит по ссылке и подтверждает пароль;
   после этого снова может входить через приложение.

Проектные решения для интеграции:

- Счётчик блокировки принадлежит Neruvalo; считаются последовательные неверные
  пароли по аккаунту со всех устройств. Успешный вход обнуляет этот счётчик.
- Ошибки картинок, сети и отмена проверки не являются неверным паролем.
- Проверка разблокировки также требует картинок.
- Офлайн-разблокировка локального хранилища не зависит от GateVeriq.
- GateVeriq не получает пароли, OPAQUE-секреты, email-коды, адреса email или
  ссылки разблокировки. Для привязки используется непрозрачный идентификатор.

## 2. Границы ответственности

| GateVeriq | Neruvalo |
|---|---|
| Выдача challenge, PoW, картинки | Регистрация, email-коды, OPAQUE |
| Обязательность картинок по политике | Журнал входов и точный счётчик 1/2/3 |
| Привязка проверки к действию и контексту | Блокировка аккаунта и серверных сессий |
| Одноразовые токены и идемпотентное потребление | Отправка писем, ссылки разблокировки |
| История риска для назначения проверок | Однократное выполнение бизнес-операции |

Не добавляй в GateVeriq SMTP, управление аккаунтами Neruvalo, проверку паролей,
порог блокировки после трёх ошибок или самостоятельную отправку уведомлений.
История риска GateVeriq не заменяет журнал и счётчик Neruvalo.

## 3. Что уже есть

Перед реализацией проверь актуальность:

- `src/website.rs`: подготовка попытки, привязка аккаунта и origin, приём
  результатов входа, назначение картинок по истории ошибок.
- `src/visual.rs`: картинки, лимит ответов, срок действия, смена доски при ошибке.
- `src/service.rs`: challenge, выдача и потребление токена.
- `sdk/server.mjs`: `prepareLogin`, `consume`, `reportOutcome`.
- `web/widget.js`, `web/worker.js`: браузерный сценарий.
- `docs/protocol.md`, `docs/website-integration.md`, `docs/integration-guide.md`.

В изученной версии `WebsitePrepare` не содержит режима обязательных картинок,
а подсчёт истории неудач аккаунта не разделён по `action`.
Существующий API уже принимает `action`: не создавай параллельные API
регистрации и восстановления, если достаточно обобщить текущий контракт.

## 4. Обязательные доработки

### 4.1. Политики картинок по интеграции и действию

Добавь сохраняемую политику для пары `(integration_id, action)`:

- `visual = adaptive`: картинки назначаются по правилам риска.
- `visual = always`: нельзя выдать успешный токен без пройденных картинок.

Пример целевой настройки Neruvalo:

| Действие | Политика |
|---|---|
| `register` | `always` |
| `email_verify` | `always` |
| `login` | `adaptive` |
| `unlock` | `always` |

Это желаемые значения для интеграции Neruvalo, а не глобальные значения по
умолчанию для всех пользователей GateVeriq. Все действия должны входить в
разрешённый список интеграции.

Управлять политикой можно через локальный CLI/административную конфигурацию.
Браузер и публичный API не могут ослаблять политику. Если добавляется параметр
на внутреннем API, он может только усиливать постоянную политику.

Политику, применённую при создании попытки, сохраняй с попыткой. Повтор создания
с тем же контекстом не должен менять её или сбрасывать лимит ответов.
Не вводи ослабление уже созданной попытки при последующем изменении настройки.

### 4.2. Принудительная проверка на сервере

Для `always` возвращай visual-задачу уже при подготовке попытки. Проверяй её
выполнение в общей серверной точке выдачи токена, включая доступные legacy-маршруты.
Одного изменения поведения виджета недостаточно.

До правильного решения картинок токен отсутствует. Сохраняются PoW, срок
действия, лимит неправильных ответов и остальные действующие ограничения.
Обновление страницы и повтор API-запроса не дают новую доску с полным бюджетом.
После исчерпания лимита/истечения срока нужен новый контекст бизнес-операции.

### 4.3. Проверяемый результат потребления

Добавь в успешный ответ внутреннего consume API серверное поле, например:

```json
{
  "valid": true,
  "action": "register",
  "context_id": "...",
  "verification_method": "pow_visual"
}
```

Предлагаемые значения: `pow` и `pow_visual`. При необходимости добавь другое
название, но однозначно отличай выполненные картинки от одной лишь политики.
Нельзя сообщать `pow_visual`, если visual-задача только назначена.

Источником значения является серверное сохранённое состояние. Поле не принимается
на доверии из браузера и не требует изменения непрозрачного формата токена.
Идемпотентный повтор consume возвращает тот же метод, действие и контекст,
включая период сохранения квитанции после истечения токена.

### 4.4. Разделение истории результатов

Раздели историю риска как минимум по `(integration_id, account_hash, action)`.
Неверный email-код или операция `unlock` не должны увеличивать историю
неудачных `login`. Проверь индексы, миграции и запросы как при подготовке
попытки, так и непосредственно при выдаче токена.

Сохрани действующую семантику GateVeriq: успешный результат не стирает историю
риска, а повтор сообщения результата не создаёт вторую запись.
Обнуление последовательного счётчика при успешном входе выполняет Neruvalo.
Не добавляй публичную возможность очистки истории.

Для старых записей действие можно восстанавливать по связанной challenge только
если связь доступна и однозначна. Не приписывай всем старым результатам `login`
без проверки; опиши выбранную миграцию.

### 4.5. SDK, виджет и примеры

- Добавь обобщённые методы подготовки попытки и отправки результата, если текущие
  названия `prepareLogin`/`reportOutcome` мешают использованию других действий.
  Сохрани совместимые обёртки для существующих клиентов.
- Проверь, что SDK сохраняет новые поля consume-ответа.
- Виджет должен проходить обязательные картинки, полученные сразу при prepare,
  и корректно показывать отмену, истечение срока, исчерпание ответов и повтор.
- Повтор страницы не должен автоматически создавать бесконечные новые попытки.
- Обнови английскую и русскую документацию, примеры конфигурации и CLI help.
- Добавь небольшой пример backend-сценария `register`/`email_verify` с фиктивной
  бизнес-проверкой. Не добавляй настоящую отправку писем или пароли.

## 5. Контракт с Neruvalo

### Регистрация и email-код

Neruvalo сохраняет случайный контекст, привязанный к неизменяемым параметрам
операции. Создаёт `register` с обязательными картинками и потребляет токен
перед разрешением регистрации/отправки письма.

На стороне Neruvalo результат проверки может давать сохранённое одноразовое
разрешение на первый ввод email-кода. После неверного кода разрешение теряется;
перед следующей проверкой создаётся новая попытка `email_verify` с картинками.
Это состояние Neruvalo, а не повторное использование уже потреблённого токена.
Допустим также более строгий сценарий с отдельной visual-проверкой перед каждым
вводом кода, но он не должен быть навязан примером как обязательное требование.

Для каждого следующего ввода используется новый контекст и новый токен.
Смена кода в запросе при прежнем request ID — не идемпотентный повтор.
Backend обязан связать request ID с неизменяемым запросом и выполнять его один раз.
GateVeriq не сравнивает email-коды и не знает, какой из них правильный.

### Вход и разблокировка

Neruvalo потребляет токен `login` перед допуском к OPAQUE-аутентификации.
Один токен разрешает одну попытку, включая привязку к аккаунту; результат
сообщается после фактического успеха/ошибки аутентификации.

После трёх ошибок Neruvalo блокирует аккаунт. Для разблокировки создаёт
самостоятельную операцию `unlock`, привязанную к валидной ссылке восстановления,
и требует картинки и подтверждение пароля. GateVeriq проверяет только
свою часть; снятие блокировки принадлежит Neruvalo.

Пароли и email-коды никогда не передаются в GateVeriq. Неизвестный логин не должен
раскрываться через различия внешнего сценария; стабильную непрозрачную привязку
для него формирует Neruvalo.

### Окно проверки desktop-клиента

В Neruvalo открывается отдельная страница проверки на origin его сервера.
У неё нет доступа к хранилищу и привилегированному Tauri IPC. Виджет и Worker
обслуживаются с этого origin; разрешённые origins задаёт backend.

После проверки backend потребляет токен и сохраняет статус. Rust-клиент
Neruvalo узнаёт статус своей попытки через аутентифицированный либо защищённый
случайным секретом канал ожидания. Одного знания публичного `operation_id`
недостаточно для присвоения или завершения чужой попытки.
Не требуется добавлять Tauri-зависимости или IPC в GateVeriq.

## 6. План реализации

1. Провести аудит существующих маршрутов выдачи токена, схемы БД, CLI и тестов.
2. Определить совместимое представление политик и миграцию БД.
3. Реализовать сохранение и настройку политики по интеграции/действию.
4. Применить `always` при подготовке и во всех путях выдачи токена.
5. Сохранить фактический метод проверки и вернуть его при consume и повторах.
6. Разделить историю результатов по действию, обновить индексы и миграции.
7. Обновить SDK, виджет, примеры и документацию.
8. Выполнить проверки и показать итоговый контракт интеграции с примерами JSON.

Не меняй криптографический протокол PoW или формулу токена без необходимости.
Сохрани текущие ограничения тела запроса, строгую валидацию, origin binding,
аутентификацию внутреннего API и отсутствие интеграционного секрета в браузере.

## 7. Обязательные тесты и критерии приёмки

- `register/always` выдаёт visual-задачу без предварительных ошибок аккаунта.
- Один PoW без картинок не даёт токен через основной или legacy-маршрут.
- Корректные PoW и картинки дают токен; consume сообщает `pow_visual`.
- Изменённые action/context/integration и чужой токен не принимаются.
- Браузер не может переключить `always` на `adaptive` или подделать метод.
- Повтор prepare с прежним контекстом сохраняет политику, срок и бюджет ответов.
- Ошибочный ответ меняет доску по текущим правилам, но не обновляет бюджет/срок.
- Истёкшая или исчерпанная задача не выдаёт токен.
- Параллельные запросы не обходят visual-проверку и одноразовое потребление.
- Точный повтор consume возвращает прежний результат, в том числе метод;
  иной request ID не получает разрешение на новую операцию.
- Новая попытка `email_verify/always` снова требует картинки после сообщённой
  ошибки кода; старый токен нельзя использовать с новым контекстом.
- Ошибки `email_verify` и `unlock` не увеличивают историю `login`.
- Повтор outcome идемпотентен; противоречивый outcome отклоняется.
- Существующие интеграции и PoW-only API работают после миграции.
- Изменение политики не ослабляет уже созданную обязательную проверку.
- Миграция проверяется на существующей БД, включая сохранённые попытки и квитанции.

Запусти применимые проверки из актуальной документации проекта, включая:

```text
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
node tests/worker.mjs
node tests/behavior.mjs
node tests/visual.mjs
node tests/sdk.mjs
cargo build --locked
python tests/e2e.py
```

Если какие-либо команды изменились, используй актуальные. На Windows учитывай
блокировку exe работающим сервером; используй отдельный target-каталог вместо
принудительной остановки чужого процесса.
