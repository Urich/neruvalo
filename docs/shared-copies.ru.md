# Общие копии Neruvalo — проект реализации

Статус: проектирование, 30.10.2026. Код общих копий пока не реализован. Документ уточняет разделы 6, 10.6 и 35 спецификации. Продуктовые решения в конце подтверждены владельцем; технические детали ниже — предложенный план реализации.

## 1. Основа

Общая копия нужна: получателю нельзя выдавать ключ оригинала, поскольку он открывает данные владельца и связан с его историей. Создаём отдельный объект с собственными идентификаторами, шифрованием и ссылкой на оригинал. Единственный источник содержимого — последняя версия оригинала. Копия доступна только для чтения, изменяется при сохранении оригинала; сам получатель может только прекратить свой доступ.

Уже принятые правила сохраняются:

- Только владелец выдаёт доступ и видит историю оригинала.
- Передаётся вся запись; согласие получателя не требуется. Получатель получает уведомление.
- Только аккаунты одного сервера; поиск по неизменяемому логину или QR с адресом/ID сервера, ID аккаунта и отпечатком ключей.
- Архивирование оригинала прекращает все его доступы. Восстановление не возвращает их.
- Удаление аккаунта необратимо. Удаление получателем копии не затрагивает оригинал и других получателей.
- Офлайн доступно последнее синхронизированное состояние без ограничения времени. Отзыв применяется при следующей успешной синхронизации; уже увиденный секрет невозможно забрать обратно.

## 2. Новая база и версии

Владелец разрешил отказаться от совместимости с текущей базой. Для следующей реализации предлагается новая схема сервера `2`, локального кеша `2` и протокол `2`. Прежние рабочие данные автоматически не преобразуются. Пересоздание базы выполняется только явно администратором/пользователем; этот документ не разрешает удалять файлы сейчас.

Разрешение относится к существующей базе прототипа, а не отменяет будущую политику версионности и совместимости. Старые клиенты должны получить явную ошибку несовместимого протокола до записи. Не позволять им сохранить оригинал без обязательных обновлений общих копий. Новые форматы, минимальная версия клиента и инструкции запуска фиксируются до реализации; текущие сборки продолжают оставаться протоколом 1.

SQLite и PostgreSQL получают одинаковую логическую схему. Никакого открытого содержимого секретов в серверных столбцах или событиях.

## 3. Сущности

| Сущность | Назначение |
|---|---|
| `records` | Оригинал, владелец, текущие `record_revision`, `version_id`, `sharing_revision`, признак архива |
| `record_versions` | Неизменяемая история владельца, зашифрованная его ключами |
| `shares` | `share_id`, оригинал, владелец, получатель, `copy_id`, состояние, ревизия доступа, привязка публичных ключей |
| `shared_copies` | Только текущий контейнер копии: `copy_revision`, версия оригинала, зашифрованное содержимое, оболочка ключа, подпись владельца |
| `account_changes` | Последовательные события синхронизации каждого аккаунта с возрастающим курсором |
| `notifications` | Уведомление о новой записи, связанное с конкретным доступом; без секретов |
| `operations` | Идемпотентность: ID операции, аккаунт инициатора, хеш запроса, окончательный результат |

На пару «оригинал–получатель» допускается только один активный доступ. Нельзя выдавать доступ самому себе, к группе целиком или к архивному оригиналу. Повтор после сетевого сбоя с тем же `operation_id` возвращает тот же результат. Повторное действие «Поделиться» с уже активным получателем показывает существующий доступ, не создаёт дубль или повторное уведомление.

После отзыва/отказа остаётся служебное состояние прекращённого доступа. Сам текущий контейнер получателя удаляется из выдачи и из таблицы текущих копий; историю владельца это не затрагивает. Новая выдача создаёт новые `share_id`, `copy_id` и ключи. Старый доступ никогда не переводится обратно в активное состояние.

Удаление аккаунта владельца удаляет его оригиналы, историю, доступы и текущие общие контейнеры; получателям добавляются события прекращения доступа. Удаление получателя прекращает только его доступы. Реальная очистка внешних резервных копий относится к согласованному администрированию и отдельно описывается оператором.

## 4. Криптографический контейнер

Для каждого активного получателя и каждой новой версии генерируется отдельный случайный ключ копии. Содержимое копии шифруется согласованным AEAD; ключ копии упаковывается готовой реализацией sealed box для `PK_share` получателя. Собственные ключи шифрования/истории владельца получателю не передаются. Не вводить собственный протокол обмена ключами или самодельную реализацию sealed box.

Подпись владельца связывает как минимум:

`format_version`, `server_id`, `owner_id`, `recipient_id`, `record_id`, `source_version_id`, `source_revision`, `share_id`, `copy_id`, `copy_revision`, ревизию доступа, ID/отпечаток ключей обеих сторон, шифротекст и оболочку ключа.

Контекст AEAD включает идентичности сервера, сторон, оригинала, доступа, копии и её версии. Используются разные доменные метки для контейнера, подписи выдачи, подписи обновления и подписи отзыва. Точное каноническое кодирование, размеры и тестовые векторы задаются перед кодированием; неоднозначная склейка строк недопустима. Sealed box не заменяет подпись.

Получатель проверяет контекст, подпись, ключ владельца и соответствие серверу/аккаунту, затем открывает ключ копии и содержимое. Неверный объект не отображается и не перезаписывает проверенную локальную копию. Проверенные максимальные ревизии сохраняются, чтобы обнаруживать откат уже известной версии; после полной потери локального состояния одна подпись не доказывает свежесть.

Поиск по логину запоминает увиденные публичные ключи. Их смена требует явного подтверждения с предупреждением; QR позволяет сравнить отпечаток. Первая выдача по одному логину всё ещё доверяет каталогу сервера. Обычная смена пароля не меняет ключи аккаунта; отдельная ротация ключей не должна проходить незаметно под видом смены пароля.

Сервер видит участников и связи доступа, проверяет полномочия, подписи и полноту обновлений, но не может доказать равенство открытого содержимого оригинала и копий. Открытые значения, секреты и ключи не включаются в логи/уведомления.

## 5. Минимальные операции протокола

| Операция | Кто вызывает | Основные проверки и результат |
|---|---|---|
| `accounts.resolve` | Вошедший пользователь | Точный логин; возвращает ID, ключи и отпечатки. Без массовой выгрузки каталога |
| `shares.list` | Владелец оригинала | Действующие получатели, состояния, ревизия набора доступов |
| `shares.create` | Владелец | Активный оригинал, ожидаемые ревизии записи/доступов, актуальные ключи, подпись и текущая копия |
| `records.save` | Владелец | Новая версия оригинала и обновления **всех** действующих копий одной транзакцией |
| `shares.revoke` | Владелец | Прекращает один доступ; другие сохраняются |
| `shares.dismiss` | Получатель | Прекращает только собственный доступ; оригинал не изменяется |
| `records.archive_batch` | Владельцы своих объектов | Архив всего выбранного поддерева и прекращение всех затронутых доступов одной транзакцией |
| `sync.snapshot` | Владелец аккаунта | Собственные объекты/история, текущие входящие копии, исходящие доступы и курсор |
| `sync.changes` | Владелец аккаунта | Изменения после курсора, включая прекращения доступа |
| `operations.get` | Инициатор | Проверка окончательного результата неизвестной операции |

Пользовательские уведомления не являются источником истины: удаление уведомления не прекращает доступ, а потеря push не мешает синхронизации. История копии отдельным API не предоставляется; API истории оригинала проверяет владельца. Получатель не может передать чужой `copy_id` в API сохранения, истории или выдачи доступа.

У каждой мутации есть уникальный `operation_id`; ожидаемые ревизии и все подписанные контейнеры входят в хеш запроса. Повторное использование ID с другим запросом отклоняется. При неопределённом сетевом результате клиент хранит зашифрованный запрос и проверяет/повторяет **тот же** запрос, не создавая новые ключи/ID как «повтор».

## 6. Атомарное сохранение и гонки

1. Клиент читает оригинал и действующий набор получателей вместе с ревизиями.
2. Готовит новую зашифрованную версию владельца и по новой копии для каждого действующего получателя.
3. Отправляет единый запрос с `expected_record_revision` и `expected_sharing_revision`.
4. Сервер в транзакции проверяет обе ревизии, ключи и точное совпадение списка обновляемых доступов с действующим набором. Пропуски, лишние или прекращённые доступы отклоняют всю операцию.
5. Одновременно сохраняет историю владельца, заменяет текущие копии, добавляет изменения/уведомления нужным аккаунтам и результат операции. Только затем делает commit.

`sharing_revision` растёт при выдаче, отзыве, отказе получателя и прекращении доступа из-за удаления аккаунта/архива. Добавление получателя не переписывает исходную версию записи. Изменение оригинала увеличивает `record_revision` и ревизии текущих копий; набор получателей от этого не меняется.

| Гонка | Результат |
|---|---|
| Два устройства изменили оригинал | Одно сохранение успешно, второе получает конфликт; автоматического объединения нет |
| Получатель отказался во время сохранения | Если отказ принят первым, сохранение со старым набором отклоняется; если сохранение было первым, последующий отказ всё равно прекращает доступ |
| Владелец отозвал доступ во время сохранения | Та же проверка набора; старый доступ не возрождается |
| Новая выдача во время сохранения | Проверка ревизий заставляет повторно подготовить запрос по текущей версии и текущим получателям |
| Архивирование и выдача доступа | Если архив принят первым, выдача запрещена; если выдача первая, архив прекращает и новый доступ |
| Архивирование группы и добавление дочерней записи | Контроль ревизии структуры/снимка поддерева не позволяет незаметно пропустить запись |

Сообщение при конфликте содержимого сохраняется: «Запись изменена на другом устройстве. Синхронизируйте устройства.» Для конфликта набора доступов предлагается отдельное сообщение: «Общий доступ изменён. Синхронизируйте устройства и повторите действие.» Черновик не стирается, сохранение блокируется до синхронизации и повторного открытия/проверки актуальных данных.

Для PostgreSQL блокировки аккаунтов, оригиналов и доступов берутся в заранее определённом порядке. При операции с несколькими аккаунтами — сортировка ID аккаунтов; после получения блокировок набор доступов перепроверяется. Не добавлять блокировки в произвольном порядке после обнаружения нового получателя: конфликт и повтор подготовки. Это предотвращает взаимную блокировку встречных выдач. SQLite выполняет тот же набор проверок в одной транзакции записи. События и курсоры не должны «съедаться» из-за commit в другом порядке: последовательность аккаунта выделяется под его блокировкой.

## 7. Синхронизация и локальное хранение

История владельца и входящие копии хранятся отдельно. Для копии хранится только текущий проверенный контейнер и оболочка ключа получателя; секретный ключ аккаунта защищается существующим механизмом разблокировки. Вложение полученной копии в таблицу полной истории оригиналов запрещено.

Клиент применяет страницу изменений и её курсор в одной локальной транзакции. Сначала проверяет подписи и формат всей страницы; при ошибке курсор не продвигает. Прекращение доступа удаляет контейнер/ключ копии из рабочего кеша и её открытое представление в памяти. Нельзя обещать физическое уничтожение всех следов на SSD, в SQLite WAL или резервной копии.

При потере курсора/истечении срока журнала сервер требует полный снимок. Снимок согласован по данным и курсору: отсутствующая в полном актуальном списке ранее полученная копия убирается. Обрыв до завершения снимка не должен сначала стирать рабочий кеш. Подписи владельца проверяются, но отключённый/скомпрометированный сервер может удерживать события и мешать свежести; это не объявляется решённым криптографией.

При заблокированном приложении секреты не расшифровываются в фоне. Уведомление ОС — нейтральное сообщение о новой записи без названия/содержимого. После разблокировки приложение показывает проверенную копию. Бессрочный офлайн-режим сохраняется.

## 8. Интерфейс

В контекстном меню и карточке собственной активной записи — «Поделиться». Диалог содержит выбор по логину/QR, отпечаток ключа, предупреждение о передаче всей записи, список текущих получателей и отдельное действие отзыва. Для криптокошелька дополнительно сообщается о последствиях раскрытия seed/приватного ключа по принятой спецификации. Подтверждение передачи показывает точного получателя и название записи.

Для собственной записи с активным доступом — индикатор и число получателей. Фильтр «С общим доступом» показывает собственные записи хотя бы с одним действующим доступом, сочетаясь с типом и поиском. Исходящие записи сохраняют собственные группы. После отзыва последнего доступа запись исчезает из этого фильтра.

В «Полученные» показываются владелец, текущее содержимое и состояние синхронизации. Нет редактирования содержимого, истории и «Поделиться» от имени владельца. «Убрать у меня» требует подтверждения и прекращает доступ только текущего получателя. Обычное копирование значения не считается передачей доступа и подчиняется настройкам буфера.

Операции доступа доступны только онлайн. Офлайн индикаторы и фильтр показывают последнее синхронизированное состояние, без обещания, что доступ ещё существует на сервере. Ошибка выдачи не создаёт фантомную копию или успешное уведомление.

## 9. Последовательность реализации

1. Зафиксировать формат 2, канонические подписи и тестовые векторы по подтверждённому составу копии.
2. Новая схема сервера и кеша, операции доступа, проверки полномочий, идемпотентность и транзакции; тесты SQLite/PostgreSQL.
3. Шифрование общих контейнеров и проверка ключей в Rust-ядре. Проверить попытки подмены сервера, сторон, оригинала, версии, копии и ключей.
4. Включить обновления копий в **каждый** путь сохранения: редактор, восстановление истории, импорт/обновление, пакетные операции. Архивирование записи/группы и удаление аккаунта одновременно прекращают доступы.
5. Снимки, курсоры, события прекращения и офлайн-кеш; тесты обрывов, повторов, откатов и повторной выдачи.
6. Диалог «Поделиться», полученные записи, исходящий фильтр, локализация и уведомления. Проверить несколько аккаунтов и устройств на одном сервере.

Не выпускать работающую выдачу доступа раньше атомарного обновления и отзыва: иначе уже выданные копии будут незаметно устаревать или возвращаться после отзыва. Никакие платёжные ограничения этим документом не вводятся.

## 10. Подтверждённые решения владельца

1. **Подтверждено владельцем:** полученные записи в первой реализации находятся в отдельном разделе «Полученные», без помещения в собственные группы. Собственные группы для них — отдельная будущая доработка.
2. **Подтверждено владельцем, вариант Б:** передавать название, тип, все содержательные поля и заметки. Группы и теги владельца остаются только у него и не передаются получателю. Это уточняет прежнее «вся запись»: речь обо всём содержимом секрета, без личной организации хранилища.

Общий контейнер строится отдельной явной проекцией: версия формата содержимого, тип, название, карта содержательных полей (включая дополнительные поля документов) и заметки. Нельзя сериализовать исходный `RecordData` целиком и затем забыть убрать метаданные. В тело копии не включаются `folder`, `group_id`, `parent_group_id`, `legacy_path`, `tags` и произвольные служебные поля оригинала. Техническая подписанная оболочка содержит необходимые ссылки на оригинал и версию по разделу 4. Организационные изменения, не меняющие содержимое копии, не раскрывают свои значения получателю. Проверки должны подтверждать отсутствие организационных полей в расшифрованном теле копии при создании и обновлении. Текст, который пользователь сам ввёл в содержательные поля или заметки, не подвергается автоматическому удалению слов, похожих на названия групп/тегов.
