# Целостность базы: формат 3

Реализация плана от 17 ноября 2026 года находится в ветке `fix/database-integrity` и основана на `b312b48`. Исходный исследованный `vault.nvdb` здесь не использовался; коммит сборки, создавшей его, не установлен. Тесты используют только синтетические секреты.

## Версии и создание

| Компонент | Версия |
|---|---|
| Протокол, серверная схема, локальная схема, профиль | 3 |
| Подпись версии записи | 2 |
| Манифест, короткая ссылка манифеста | 1 |
| Локальная резервная копия | 2 |
| Внутренний payload с отдельными блоками файлов | 3 |
| Общий контейнер | 2 |
| Криптографический AEAD-конверт | 1 |

Версии независимы. Старые dev-профили, базы, подписи и резервные копии отклоняются без миграции. Отсутствующий манифест существующей базы никогда не восстанавливается автоматически. Отсутствующие серверные ключи/OPAQUE setup также не генерируются заново поверх существующей базы.

SQLite использует STRICT, `NOT NULL` первичные ключи, положительную целочисленную ревизию, уникальную пару `(record_id, revision)`, `CHECK(json_valid(body))` и индекс для поиска последних версий. Уникальный индекс `(record_id, revision)` обслуживает обратный поиск последней версии и упорядоченную историю: это проверено через SQLite EXPLAIN QUERY PLAN. Дублирующий `versions_latest` не создаётся. Поставляемая SQLx-сборка использует SQLite с STRICT и JSON; это проверяется тестами создания/ограничений. PostgreSQL использует BIGINT и соответствующие ограничения JSON. Маркер готовой серверной схемы, серверная идентичность и OPAQUE setup публикуются одной транзакцией. Незавершённая или неизвестная база отклоняется.

Для пересоздания dev-окружения остановите клиент и сервер, сохраните старые файлы отдельно и выберите новые пути для локального `.nvdb`, клиентского каталога данных и `database_url` сервера в TOML. Для PostgreSQL используйте отдельную пустую dev-базу. Затем создайте локальное хранилище либо заново зарегистрируйте тестовые аккаунты на новом сервере. Приложение не удаляет старые файлы, кеши или внешние ориентиры. Исходный файл старого формата не подходит для восстановления в формат 3.

## Проверенный путь чтения

Общий код `crates/protocol/src/integrity.rs` проверяет UUID, поддерживаемую версию подписи, размеры, Ed25519-подписи и непрерывную историю. История начинается с ревизии 1 и пустой ссылки; каждая следующая версия ссылается на непосредственного предшественника того же объекта. Дубли, разрывы, циклы и развилки отклоняются.

Локальный загрузчик сравнивает SQL `id`, `record_id`, `revision` с подписанным JSON до использования версии. Полный состав и головы сверяются с манифестом в том же снимке транзакции, в котором читаются данные. Проверяются все исторические подписи; расшифровываются только необходимые текущие метаданные и явно запрошенное содержимое. Отдельный кеш хранит компактные проверенные заголовки и fingerprint точных байтов JSON, без расшифрованных исторических секретов. Изменение любых байтов требует повторной проверки; SQL-колонки проверяются и при попадании в кеш.

На сервере проверяются история владельца, подписи, принадлежность аккаунту и SQL-головы. Кандидат нового манифеста должен следовать предыдущему и точно описывать состояние после записи. Блокировка записи берётся до проверки ожидаемой ревизии. Данные, служебное состояние операции и манифест обновляются одной транзакцией при сохранении, пакетных групповых изменениях и импорте. Идемпотентный повтор использует те же идентификаторы и тот же кандидат манифеста.

## Канонизация и подписи

Точные правила задаёт `canonical_json` в protocol: UTF-8 без пробелов, JSON-экранирование строк через serde_json, сортировка ключей объектов по строковому порядку, сохранение порядка массивов. Все поля чисел этого формата — целые JSON-числа без дробей/экспоненты. UUID представлены строками; `null` отличается от пустой строки. Манифест не содержит произвольных чисел с плавающей точкой. Независимый Python-вектор байтов и hash находится в `docs/test-vectors/vault-manifest-v1.json` и проверяется Rust-тестом.

Подпись версии 2 включает версию формата, идентичность сервера/аккаунта, operation/record/version ID, ожидаемую ревизию, предыдущую версию, канонический payload, архивный признак и `created_at`; точный порядок и домен зафиксированы `record_transcript`. `created_at` — подписанная клиентская дата в секундах Unix, а не доказательство точного времени события. Сервер сохраняет её без замены своими часами. Сам манифест исключён из transcript записи, чтобы не создавать циклическую зависимость.

Digest компонента истории вычисляется по transcript и подписи, затем накапливается в цепочку с доменом `neruvalo-history-v1`. Голова содержит ID версии, ревизию, число версий, digest всей истории и архивный признак. Digest не зависит от расположения страниц SQLite. Зашифрованные блоки файлов и их идентификаторы входят в подписанный payload; имена файлов остаются внутри зашифрованных метаданных.

Подписываемый манифест — канонический JSON-массив:

```
["neruvalo-vault-manifest-v1", manifest_version, vault_id, server_id,
 account_id, generation, previous_manifest_hash, records,
 metadata_digest, auxiliary_digest]
```

`vault_id` равен `account_id`, контекст дополнительно содержит `server_id`. Поколение начинается с 1, у первого состояния предыдущий hash пустой. `metadata_digest` связывает сервер, аккаунт, публичные ключи подписи и обмена с доменом `neruvalo-profile-v3`. Hash манифеста вычисляется по каноническому JSON-массиву из UTF-8 строки transcript и подписи. `link_signature` подписывает короткую ссылку отдельно, с доменом `neruvalo-manifest-link-v1`, контекстом сервера/аккаунта, поколением, предыдущим и текущим hash.

Локальный `auxiliary_digest` покрывает все `meta`, кроме `schema_version` (отдельно проверяется строго) и самого `manifest`: это digest канонического упорядоченного отображения `имя → digest(значение)`. Для `local_profile` значение сначала канонизируется без локального alias `id` и настройки `timeout_seconds`; KDF, парольный конверт, ключи, форматы и идентичность защищены. Кеш общего доступа, pin/guard и минимальные журналы незавершённых операций тоже покрыты. В серверном манифесте владельца auxiliary пуст: локальные настройки не передаются серверу.

Получатель общей записи имеет частичное представление: подпись отправителя, контекст получателя, pinned ключи и правила lifecycle проверяются отдельно. От него не требуется полная история владельца. Полученный снимок общего доступа защищается локальным манифестом кеша; полнота удалённого списка участников/отзывов остаётся серверной гарантией. Манифест истории владельца не является криптографическим доказательством полного удалённого графа общего доступа.

## Пароль и резервная копия

Обязательное описание KDF содержит `argon2id`, версию 19, memory KiB, iterations, parallelism, output length и соль. По умолчанию сохранены прежние параметры: 65536 KiB, 3 прохода, p=1, 32 байта, случайная соль 16 байт. Перед вычислением допускаются только memory 65536–262144 KiB, iterations 3–10, p=1–4, output=32 и соль ровно 16 байт. Значения вне диапазона отклоняются до выделения памяти Argon2. Подбор новых defaults по Windows/мобильным устройствам не выполнен; увеличение p не объявляется усилением защиты.

Полное описание KDF включено в AEAD-контекст парольного конверта `neruvalo-password-envelope-v2`; резервная копия использует отдельный контекст формата 2 с той же привязкой. Смена локального пароля/KDF переупаковывает только root key с новой солью/nonce; подписи, ключи записей и история сохраняются. Авторитетный профиль встроен в базу, внешняя копия является зеркалом. Смена пароля и экспорт backup перечитывают его из проверенного снимка БД, включая изменение пароля другим открытым экземпляром приложения. Профиль и манифест меняются транзакционно, зеркало записывается атомарной заменой после commit.

Резервная копия снимается в одной проверенной транзакции: профиль, все версии, защищаемые metadata, манифест и подписанные ссылки. При восстановлении всё проверяется до публикации. Восстановление — явная операция восстановления старого состояния; она разрешает сброс соответствующего внешнего ориентира. Обычное открытие такого разрешения не имеет. Старые резервные копии явно отклоняются.

## Откат и восстановление после сбоя

В каталоге данных приложения `integrity/` лежат подписанные контрольные ссылки, отдельно для локального кеша и серверного состояния владельца. Имя зависит от контекста хранилища, а не пути файла: перемещение базы на том же устройстве не сбрасывает известный ориентир. На Unix каталог имеет права 0700, файлы — 0600. Обновление сериализовано файловой блокировкой, повторно проверяет актуальный ориентир под блокировкой, использует временный файл, fsync и атомарную замену; на Unix синхронизируется каталог.

Ориентир обновляется после commit. Если процесс завершился между commit и обновлением, следующий вход проверяет непрерывные подписанные короткие ссылки из журнала манифестов и продвигает ориентир. Произвольного большего номера недостаточно. Меньшее поколение или другая ветка того же поколения дают `VAULT_ROLLBACK`; отсутствие доказуемого продвижения даёт ошибку целостности. Если запись ориентира не удалась, данные уже могут быть зафиксированы: устраните ошибку доступа/места и повторно откройте базу, продвижение будет проверено по журналу.

Первое открытие на новом устройстве или после очистки данных приложения устанавливает исходный ориентир. Последующие открытия проверяют состояние относительно него. Интерфейс сообщает о нарушении целостности или обнаруженном откате. Это защита от отката одного файла при сохранном локальном ориентире. Если атакующий откатывает и БД, и каталог `integrity/`, гарантии свежести нет. Каталог не является OS keychain и не защищает от администратора или скомпрометированного процесса.

Для онлайн-владельца сервер сериализует изменение манифеста по generation/previous hash; проигравшее устройство получает конфликт и должно синхронизироваться. Подписанные ссылки позволяют другому устройству проверить продвижение от собственного ориентира. При недоступном сервере офлайн-кеш проверяется относительно локального ориентира, но не доказывает отсутствие новых удалённых изменений. Для независимых копий локальной базы общего глобального порядка нет; конкурирующие ветки обнаруживаются при наличии ориентира, автоматическое слияние не выполняется.

## Отчёты импорта и ресурсы

Полный отчёт KeePass и сводка живут только в памяти текущего разблокированного сеанса. HTML передаётся в sandbox iframe через IPC, файлы не создаются. Новый импорт/закрытие результата освобождает отчёт; блокировка/перезапуск уничтожает его. Сохраняется только зашифрованный минимальный журнал: ticket, допуск подтверждения, состояние отправки и точный запрос для продолжения без дубликатов. В нём нет текста отчёта, подробностей, путей исходной базы и сводки счётчиков. После перезапуска UI показывает состояние операции и отсутствие отчёта. Отчёты не попадают в резервные копии и журнал приложения. Максимум подробностей — 1000 и примерно 256 KiB текста; число скрытых событий видно пользователю.

Текущие лимиты преднамеренно различаются по операциям:

- версия JSON ≤8 MiB; полная проверенная история ≤200000 версий и ≤512 MiB сериализованных версий;
- манифест/HTTP-ответ ≤32 MiB; серверный snapshot версий ≤24 MiB с дополнительным бюджетом общих копий; итоговый ответ всё равно ограничен клиентом 32 MiB;
- metadata ≤10000 значений, ключ ≤256 байт, значение ≤32 MiB, сумма ≤64 MiB;
- журнал коротких ссылок ≤100000 записей, отдельная ссылка ≤4 KiB; автоматического pruning пока нет;
- профиль ≤64 KiB; вход backup ≤64 MiB, собираемое содержимое backup ≤32 MiB; большие локальные базы можно использовать, но backup/import/full server sync сверх соответствующего бюджета отклоняются явно;
- вложения ≤1 MiB на файл, ≤4 MiB и ≤16 файлов на запись; отчёт ≤1000 подробностей/примерно 256 KiB;
- рекурсивный JSON-разбор использует стандартный предел serde_json; KDBX сохраняет отдельные пределы KDF, распаковки и глубины XML.

История проверяется потоково в согласованном снимке. HTTP читается ограниченными chunk, файлы профиля/backup — через bounded reader. Количество проверенных заголовков ограничено. Полный серверный snapshot, backup и запрос импорта остаются ограниченными материализованными пакетами; потоковый сетевой протокол здесь не вводился.

## Проверки и измерения

Добавлены mutation-тесты SQL/JSON, даты и исторической подписи, удаления записи/хвоста/начала, отсутствующего манифеста, постороннего контекста; тесты цепочек, канонизации, ограничений SQL/KDF, старых схем без исправления, целого отката, ветвления, первого устройства, commit-before-anchor, конкуренции и SQLITE_FULL. Существующие E2E проверяют регистрацию/OPAQUE, сохранение, офлайн, восстановление, группы, общий доступ и идемпотентный импорт. Детерминированный корпус некорректных parser-входов дополняет тесты; длительная fuzz-кампания и независимый аудит не проводились.

Синтетический Linux-замер отладочной сборки (`measure_database_scale`, миллисекунды; это один запуск каждого сценария, не release-бенчмарк):

| Объекты / версии | Построение | Открытие с проверкой | Индекс после открытия | Сохранение | Размер БД | VmHWM процесса |
|---|---:|---:|---:|---:|---:|---:|
| 349 / 349 | 358 | 552 | 82 | 317 | 569344 B | 90416 KiB |
| 10000 / 10000 | 10736 | 13075 | 2333 | 7513 | 15380480 B | 116988 KiB |
| 10000 / 100000 | 87233 | 50066 | 5190 | 22131 | 151441408 B | 175576 KiB |
| 1 / 1, вложения 4×1 MiB | 2705 | 1905 | 91 | 244 | 5627904 B | 116656 KiB |

VmHWM включает построение фикстуры и тестовый процесс. Открытие 100000 версий пока медленное; инкрементальное дерево и уменьшение стоимости повторного сканирования требуют отдельной работы. Приёмочные пороги на целевом оборудовании ещё не утверждены.

Отдельный SQLite STRICT микрозамер случайного блока 4 MiB: JSON с Base64 — 5603328 байт файла, запись/чтение 4,15/4,08 ms; BLOB — 4206592 байта, 1,84/0,77 ms. Это около 25% экономии хранения отдельного блока, без учёта индексов, AEAD и подписей реального payload. Для текущего формата оставлено единое каноническое JSON/Base64-представление: отдельная бинарная проекция потребовала бы сборки точных подписанных байтов при обмене и проверки согласованности второй структуры. Исторические payload не перекодируются. Переход крупных блоков в BLOB остаётся возможной отдельной оптимизацией, а не заявленным ускорением текущей реализации. `VACUUM` не гарантирует удаления с SSD, snapshots или backup.

На Linux прошли Rust workspace-тесты (без Tauri runtime), строгий Clippy, `cargo check -p neruvalo-desktop --features desktop`, все 162 UI-теста и production build. Отдельно прошли регистрация/подтверждение/вход с реально запущенным локальным GateVeriq на временной Neruvalo БД. Workflow включает Windows и PostgreSQL 17; эти окружения здесь не запускались. Измерения KDF на мобильных устройствах, приёмочные пороги, независимый криптографический обзор и проверка реального исследованного файла остаются отдельными пунктами приёмки. Прохождение тестов не является полным аудитом безопасности.

Воспроизведение проверок:

```sh
cargo fmt --all --check
cargo clippy --locked --workspace --exclude neruvalo-desktop --all-targets -- -D warnings
cargo test --locked --workspace --exclude neruvalo-desktop
cargo check --locked -p neruvalo-desktop --features desktop
(cd apps/desktop && npm test && npm run build)
NERUVALO_BENCH_SCENARIO=100000 cargo test --locked -p neruvalo-client --lib measure_database_scale -- --ignored --nocapture
```

Параметр сценария также принимает `349`, `10000`, `attachments`. Синтетический
замер строит временную базу; рабочие данные не затрагиваются. E2E требуют
локальных TCP-сокетов. PostgreSQL-тесты запускайте только с отдельной тестовой БД:
они очищают её схему. Доступ к Docker daemon в текущем окружении отсутствует;
это не проверка корректности PostgreSQL. Windows остаётся для CI/целевого устройства.
