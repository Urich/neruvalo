# Atomic group archive operations (prototype 0.3.0)

`POST /api/v1/records/batch` is an additive protocol-1 endpoint. Existing record formats and SQL schema versions remain unchanged. Group state uses the signed `archived` flag already present in stored versions. Clients need a 0.3.0 server for archive operations and writes involving groups; older servers reject the new endpoint without a partial write. Older clients do not understand group rules and should not be used with grouped vaults.

The authenticated request contains `operation_id`, `snapshot` (a map of all opaque record IDs to their current revisions), and `records` (ordinary encrypted and signed `SaveRecord` objects sharing the operation ID). No titles, folder paths or parent relationships are sent in plaintext. Each changed object receives a new immutable version; unchanged objects receive none.

The client computes the subtree from decrypted local metadata, including legacy folder projections. Archiving selects all descendants, independently of UI filters. Restoring a group selects its entire current subtree, including records archived earlier. Restoring an individual entry selects only that entry and its ancestor groups. Restoring a subgroup selects that subtree and its ancestors. Sharing is not yet implemented in this prototype; future revocation must participate in this transaction, and restore must never recreate old shares.

The server validates all signatures, then begins a database transaction and obtains a write lock on the owning account row (`UPDATE accounts SET id=id WHERE id=...`). Every single-record write uses the same account lock. After checking the operation journal for a replay, the server compares the complete current revision map with `snapshot`, applies every change and records one operation result before committing. A mismatch rolls back the complete operation. This deliberately conservative check also detects unrelated vault changes and insertion of a new child; it avoids relying on a parent revision alone. Group-linked single-record saves use a one-element batch, so a stale device cannot add a child to a group archived by another device in the meantime.

SQLite and PostgreSQL use the same SQL transaction flow. Maximum batch size is 10,000 changed objects, also subject to the existing HTTP body limit. A rejected oversized batch has no partial effects. The UI reports the error; it never splits an archive operation into uncoordinated writes.

Before sending, the client persists the exact encrypted request in `pending_operation`. Transport/server failures preserve it and disable further edits. Synchronization checks `/api/v1/operations/:id`; if absent, it replays the same request to the correct single/batch endpoint. Same operation ID with a different request is rejected. A definitive rejection permits fetching a fresh snapshot; an unresolved request stays pending. Old single-record pending requests remain readable.

The archive view retains active ancestor groups as navigation context for descendants still archived. Empty active/archived groups appear only in the corresponding unfiltered view; a type filter hides groups without matching descendants. Choosing a group in the archive restores its entire subtree, even when the group itself is already active as context. Creating an item never attaches it to an archived group. For a historical version of an archived entry, restore the entry first, then restore the desired historical version.

Checks include nested/empty groups, individually prearchived entries, partial restoration, stale snapshots with newly created children, stale group-linked saves after archive, offline rejection, history retention and both database backends in CI.
